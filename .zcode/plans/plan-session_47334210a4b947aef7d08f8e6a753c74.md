# QB Flex — Production and Staging Docker/Compose Deployment Plan

## Goal
Make the existing Docker and Compose setup proper and functional for both production and a simpler local staging environment, then validate the staging deployment end-to-end.

## Decisions from clarification
- **Staging**: localhost/127.0.0.1 ports, no TLS, no gateway. Otherwise mirrors production (NODE_ENV=production, required secrets, resource limits, hardening).
- **CI/Registry**: out of scope; keep Compose-only on-host builds.

## Current state
- `compose.yml` — local development with Mailpit, API, worker, Studio, Docs, storage-init.
- `compose.selfhost.yml` — production overlay with Caddy gateway, TLS, resource limits, hardening, required secrets.
- `infra/Dockerfile` — multi-target Bun image (source → verify → api/worker/web-build → studio/docs/storage-init). Runtime stages currently inherit the full source tree and all dev dependencies.
- Only the `api` service has a healthcheck. Init ordering for `storage-init` is not enforced. No staging overlay exists.

## Implementation plan

### 1. Harden and slim the Dockerfile (`infra/Dockerfile`)
Keep the existing pinned `oven/bun:1.4.2` base image and multi-target shape, but split build/runtime more cleanly:

- Add an explicit `builder` stage that runs `bun install` and produces all distributable artifacts (`sdk:build`, `docs:generate`, `apps/studio` build, `apps/docs` build).
- Add a `runtime-base` stage that installs only production workspace dependencies (`bun install --production`) and copies only the package manifests / workspace metadata needed at runtime.
- Add a non-root application user (`qb` / UID 10001, GID 10001) instead of inheriting the generic `bun` user. Create `/var/lib/qb-flex` owned by this user.
- Set `NODE_ENV=production` in all runtime stages (`api`, `worker`, `studio`, `docs`, `storage-init`).
- Make each runtime target copy only what it needs:
  - `api`: production `node_modules`, `apps/api/src`, required `packages/*` runtime code, `migrations/`.
  - `worker`: production `node_modules`, `apps/worker/src`, required `packages/*`.
  - `studio`: production `node_modules`, `apps/studio/dist`, `apps/studio/server.ts`, and server manifest.
  - `docs`: production `node_modules`, `apps/docs/dist`, `apps/docs/server.ts`, and server manifest.
  - `storage-init`: production `node_modules`, `scripts/storage-init.ts`, required `packages/*`.
- Add a `HEALTHCHECK` instruction in each runtime stage that hits the service's readiness or root endpoint (Studio/Docs can reuse their existing HTTP listener; worker uses a lightweight process check or API `/ready` via a small script).
- Keep the `verify` target for CI but ensure it does not leak into production images.
- Update `.dockerignore` if new build artifacts need explicit exclusion.

### 2. Add staging overlay (`compose.staging.yml`)
Create a new overlay that combines with `compose.yml` and behaves like production but on localhost:

- Use `127.0.0.1` ports directly (no Caddy gateway):
  - API: `127.0.0.1:7612:7612`
  - Studio: `127.0.0.1:7610:7610`
  - Docs: `127.0.0.1:7611:7611`
- Set `NODE_ENV=production`.
- Set public URLs to `http://localhost:<port>`:
  - `QB_PUBLIC_URL=http://localhost:7612`
  - `QB_STUDIO_URL=http://localhost:7610`
  - `QB_ALLOWED_ORIGINS=http://localhost:7610,http://127.0.0.1:7610,http://localhost:7611,http://127.0.0.1:7611`
- Set build args for Studio/Docs to the same localhost URLs.
- Require the same core secrets as production (`QB_MASTER_KEY`, `QB_BOOTSTRAP_TOKEN`, `QB_WORKER_TOKEN`, S3 credentials, mail provider) so staging validates the same production path.
- Apply the same security hardening and resource limits as `compose.selfhost.yml`.
- Use profile `staging` so it does not interfere with local development.

### 3. Add staging environment template
Create `.env.staging.example` mirroring `.env.production.example` but with localhost defaults and clear comments that this is for pre-production validation on a single host.

### 4. Improve production Compose (`compose.selfhost.yml`)
- Add healthchecks to `worker`, `studio`, and `docs`.
- Make `api`, `worker`, `studio`, and `docs` explicitly depend on `storage-init` completing (`condition: service_completed_successfully`), so bucket initialization finishes before services start.
- Add `restart: unless-stopped` to `storage-init`? No — keep it as a one-shot (`restart: 'no'`), but ensure the condition is used correctly.
- Confirm `gateway` continues to block `/internal/*` and proxy to the three services.

### 5. Update base Compose (`compose.yml`)
- Add `condition: service_completed_successfully` for any service that requires storage-init to finish.
- Add basic healthchecks to `studio` and `docs` (these will be overridden/enhanced by the overlays).
- Keep `mailpit` and `local` profile untouched.

### 6. Update docs
Update `apps/docs/content/self-hosting/deployment.mdx`:
- Add a **Staging** section explaining how to copy `.env.staging.example` to `.env`, set required secrets, and run:
  ```sh
  docker compose -f compose.yml -f compose.staging.yml --profile staging config --quiet
  docker compose -f compose.yml -f compose.staging.yml --profile staging build
  docker compose -f compose.yml -f compose.staging.yml --profile staging up -d
  ```
- Clarify that staging uses no gateway/TLS and is intended for validating secrets and production-like behavior before pointing real domains at `compose.selfhost.yml`.
- Mention that `storage-init` must complete before the API reports ready.

### 7. Test the deployment
Run the following validation in order (stopping if any step fails):

1. **Config validation**
   - `docker compose -f compose.yml -f compose.staging.yml --profile staging config --quiet`
2. **Build**
   - `docker compose -f compose.yml -f compose.staging.yml --profile staging build`
3. **Smoke test**
   - Copy `.env.staging.example` to `.env`, generate local secrets with `openssl rand -hex 32`, and point `QB_S3_ENDPOINT` at a reachable S3-compatible backend (or a local MinIO/RustFS container if one is available).
   - `docker compose -f compose.yml -f compose.staging.yml --profile staging up -d`
   - Wait for healthchecks, then:
     - `curl -fsS http://localhost:7612/ready`
     - Verify `storage-init` logs show bucket initialization.
     - `curl -I http://localhost:7610` and `http://localhost:7611` return 200.
   - Run `POST /setup` with the bootstrap token to create the first owner.
   - Sign in to Studio and confirm the workspace loads.
4. **Tear down**
   - `docker compose -f compose.yml -f compose.staging.yml --profile staging down`
5. **Production config regression**
   - `docker compose -f compose.yml -f compose.selfhost.yml --profile selfhost config --quiet` (with a populated `.env`) to ensure the production overlay still parses after the base changes.

If Docker daemon or a reachable S3 endpoint is unavailable during the test phase, document which steps were run and which were skipped.

## Files to change
- `infra/Dockerfile`
- `.dockerignore` (possible minor updates)
- `compose.yml`
- `compose.selfhost.yml`
- `compose.staging.yml` (new)
- `.env.staging.example` (new)
- `apps/docs/content/self-hosting/deployment.mdx`
- `apps/docs/src/generated/manifest.json` and search index (regenerated by `bun run docs:generate`)
- Possibly `VERIFICATION.md` or `docs/expanded-release-status.md` if deployment status is tracked there.

## Out of scope
- Kubernetes, cloud-specific container services, Terraform, GitHub Actions CI/registry (per user choice).
- Adding bundled MinIO/S3 service (operator still provides external object storage).
- Log shipping / observability sidecars (kept as future ops work).
- Multi-arch image builds.

## Acceptance criteria
- `docker compose -f compose.yml -f compose.staging.yml --profile staging config` succeeds.
- Staging images build successfully.
- Staging services start, API `/ready` responds, Studio and Docs respond, and first-owner setup works.
- Production overlay config still validates.
- Docs are updated with staging instructions.
- No `.env` secrets are committed.
