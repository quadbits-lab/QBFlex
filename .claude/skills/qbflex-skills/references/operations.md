# CLI, setup and operations

Use [generated CLI help](generated/cli.md) for exact subcommands and flags. In the source checkout prefix commands with `bun run qb`; examples below abbreviate this to `qb`. These commands manage platform resources, not browser app authentication.

## Local setup and packages

Use pinned Bun 1.4.2 and `bun install --frozen-lockfile`. Copy `.env.example` to `.env` only when no user configuration exists, then configure backend dependencies. `docker compose up -d mailpit storage-init` supplies local Mailpit. Object storage is any S3-compatible provider you configure (`QB_S3_ENDPOINT`, e.g. RustFS on 127.0.0.1:9000). `bun run dev` starts Studio 7610, Docs 7611 and API 7612; supporting host ports are SMTP 7615, Mailpit 7616. React/Vanilla examples use 7617/7618. Do not mix a native `.data` directory with an active Compose database volume.
The native launcher checks all application ports before starting children and authenticates the API-generated worker credential before launching worker/frontends. If the full local Compose stack owns the ports, use its apps directly or run `docker compose stop studio docs api worker` before `bun run dev`. This keeps infrastructure and persistent volumes intact. Independent workers require the API to start first with the same `QB_DATA_DIR`, or a matching server-only `QB_WORKER_TOKEN`; never mint a worker credential independently.

First-owner setup uses the locally generated bootstrap token through `/setup`; keep it private. Use Studio to configure project exposure/policies/origins and credentials. On macOS `qb login --url <api> --email <email>` uses an interactive hidden password and OS keychain. MFA users obtain a Studio-issued management token. On Linux supply a scoped `QB_MANAGEMENT_TOKEN`; keychain login is not implemented there. `qb link --project <id> --branch <id> --url <api>` writes non-secret `qb.json`.

Build/package SDKs with `bun run sdk:build` / `bun run sdk:pack`; local tarballs appear under `dist/packages`. Install both tarballs together with npm for React's client peer. No npm publication occurs. Skill commands are `skill:refresh`, `skill:check`, `skill:test`, `skill:pack`; see [maintenance](platform.md).

Useful actual commands: `qb projects list`, `qb db migrate --file <sql> --id <id>`, `qb types generate --output <file>`, `qb branches list`, `qb storage list`, `qb backup create`, `qb backup restore --backup <id>`. Scope to `--project`/`--branch`. `db diff` compares a supplied schema JSON; it does not generate arbitrary safe migrations. `storage sync --bucket <id> --directory <dir>` adds missing objects and preserves existing/remote-only objects. `db reset --data-dir <dir> --confirm-local-reset` destroys local data and requires explicit applicable authorization.

## Linux deployment and monitoring

Use `docker compose -f compose.yml -f compose.selfhost.yml --profile selfhost build` and `up -d` after setting public domains, exact application origins, master/bootstrap/worker keys, S3 and email credentials (Resend API key or SMTP). Core services carry no profile, so bare `docker compose up` (Dokploy/Coolify/Portainer, or `compose.yml` alone behind an external proxy) starts API, worker, Studio, Docs and `storage-init`; only Mailpit (`local`/`dependencies`) and the Caddy gateway (`selfhost`) stay opt-in. Platform deployments should use `.env.dokploy.example`, keep `QB_BIND_ADDRESS=127.0.0.1`, route API 7612, Studio 7610 and Docs 7611 in the platform proxy, and not add the selfhost overlay. For pre-domain validation, `compose.staging.yml` mirrors production secrets, limits and hardening on loopback ports without TLS or a gateway; it uses the isolated `qb-flex-staging` Compose project and sets `QB_ALLOW_INSECURE_HTTP=true`, which the API permits only for loopback URLs. Studio and Docs bake `VITE_*` public URLs at build time, so change them before building. Caddy fronts HTTPS domains; 80/443 are public TLS gateway ports, separate from the local 7610 base. One API node owns persistent PGlite disk. API, worker and Studio wait for `storage-init` to finish. Preserve volumes on restart; never use `down -v` as a port-change or deployment step.

Readiness is `/ready`; private metrics are `/internal/metrics` with the worker bearer token on a private network. Gateway internal routes return 404. Inspect request IDs, redacted logs, operation status, database directory usage, owner queue pressure, outbox lag and upload/snapshot failures. Bounded limits return predictable 429/503. Reduce workload and reconcile uncertain writes before retrying. Do not tune beyond measured deployment capacity without a workload-specific benchmark.

## Recovery: three distinct assets

1. **Database snapshots:** owner-created `dumpDataDir()` snapshots encrypted with AES-256-GCM, checksummed and schema-versioned. Restore to a new isolated branch and verify integrity, foreign keys, migrations, policies and representative rows. Auth users persist; sessions/challenges/OAuth tokens do not. Restored object metadata is unavailable until separately recovered. Never copy a live PGlite directory; use owner-created snapshots.
2. **Object bytes:** S3 bytes are not included in branch/control archives. Maintain separate object-store backups/versioning and verify bytes, metadata and availability against a compatible checkpoint. Reconciliation is not proof that missing bytes were restored.
3. **Master key:** protect the original encryption key independently and test its availability in recovery drills. A snapshot without its original key is not a usable encrypted recovery point; the archive does not include key custody.

Primary cutover requires owner role and explicit project-slug confirmation, creates a rollback snapshot, fences/retires the old primary and switches the alias. Existing sessions/sockets belong to their immutable branch; establish new sessions and reconcile clients. Rollback restores the saved snapshot into another isolated branch; alias switching is not a data merge. Prepare a comparison/recovery drill before any authorized cutover.

Control catalog recovery is offline: stop API/worker, preserve all referenced branch files, verify archive and original master key, then use `qb backup control-restore --data-dir <dir> --file <archive> --confirm-local-control-restore` only with explicit authorization. The OS lease rejects recovery over an active owner. Recovery validates catalog/schema/files, makes an encrypted rollback checkpoint, excludes sessions and revokes restored project/management credentials. Reissue credentials afterward. Control archives contain neither branch databases nor S3 bytes. Daily/weekly retention defaults are seven days/four weeks; local archives alone are not off-site disaster recovery.

## Expanded foundations

`qb doctor --directory <target>` is a read-only redacted source-CLI inventory; `--probe-url <bare-origin>` explicitly probes readiness. It does not send mail/push or prove S3/device connectivity. Exit0/1/2 means no blocking errors/errors/invalid invocation. Unknown findings remain unknown. The detached `scripts/diagnose.mjs` inventory remains compatible.

Uploads use private local staging with120second bounds; provision headroom for four≤100MiB transfers plus database files/backups. Branch archives now use authenticated streamed format2 and preserve legacy restoration. Control archives now also stream in format2 with authenticated kind/checksum/time metadata and incremental legacy-envelope recovery. Offline create/restore waits for completion; restore checks dependencies, records an encrypted rollback, revokes capabilities and holds the volume lease throughout. Control limits default1GiB/120seconds; engine snapshot export and integrity checks remain synchronous. Restore strips durable jobs in addition to sessions/provider tokens. Keep original master-key custody and object backups separate.

Durable jobs are an experimental owner foundation, not finished webhooks/push/alerts. Keep push disabled. A distinct push worker token only grants push job claims/completions; it does not create a delivery service. Continue blocking internal APIs at the public proxy. The expanded release requires all specified features and acceptance evidence.

## SQLite engine transition

Use `qb db migrate-engine --from sqlite --to pglite --data-dir SOURCE --output-dir DESTINATION --check` with stopped writers. Omit `--check` to convert into a separate empty directory. The command verifies data/constraints, preserves source files, credentials, durable checkpoints and historical archives, and publishes a completion marker. Unsupported objects/values block conversion. New SQL is PostgreSQL. Activate separately through `QB_DATA_DIR` and retain the original key and old binary/source for rollback before new writes.

`QB_MAX_BRANCH_OWNERS` defaults to four and accepts 1–32. Independent PGlite instances and full snapshot Blobs have substantial memory cost; measure on the target host.
